# SERM Distribution Engine

Инструмент для SERM-дистрибуции: генерирует статьи под несколько площадок, публикует их, пингует быструю индексацию и ведёт читателей в Telegram-воронку. Для компаний и личных брендов, которые хотят управлять тем, что поиск показывает по их имени. Настраивается профилем бренда (YAML), без правки кода.

> Перед использованием прочитайте [DISCLAIMER.md](./DISCLAIMER.md): автоматизация публикаций на сторонних площадках — ваша ответственность.

## Возможности

- **Статьи под 7 площадок** из одной кампании: VC.ru, Spark.ru, Дзен, E-xecutive, Т-Банк Секреты, Biz360, RB.RU. Часть публикуется напрямую, часть уходит как редакционный питч.
- **Два режима генерации**: `template` (встроенные Jinja2-шаблоны) и `llm` (содержание пишет модель через любой OpenAI-совместимый API; ссылки, оффер и контакты вставляет шаблон, а не модель).
- **Профиль бренда** (`person` / `company`): голос, тезисы, запретные слова и темы, уровни оффера, лид-магниты, включённые площадки.
- **Telegram-бот воронки**: проверка подписки на канал и выдача лид-магнита, аналитика переходов.
- **Быстрая индексация** опубликованных ссылок и **радар инфоповодов** на RSS.
- **Автопилот** (статьи, лид-магнит, посты для канала, экспорт, публикация) и **админка** на aiohttp.

## Стек

- Python 3.12+ (`requires-python` в [pyproject.toml](./pyproject.toml))
- aiogram 3, aiohttp, Playwright (Chromium для входа и публикации), SQLite
- pydantic / pydantic-settings, Jinja2, PyYAML
- LLM-клиент на стандартной библиотеке (`urllib`), без SDK провайдеров

## Быстрый старт

```bash
git clone https://github.com/alexrexby/serm-engine
cd serm-engine
python3 -m venv .venv && source .venv/bin/activate
pip install -e .
playwright install chromium
python cli.py init
python cli.py doctor
python cli.py login vc
python cli.py autopilot --campaign <ID кампании>
```

Установка только из исходников: `pip install -e .`. Каталог `templates/` не упаковывается в пакет, поэтому обычный `pip install .` не подойдёт.

Что делает каждый шаг:

1. `init` — мастер: тип бренда, название, канал и контакт Telegram, токен бота (проверяется через `getMe`), площадки. Создаёт `profiles/<имя>.yaml`, копирует встроенные тексты в `profiles/<имя>/templates/` (это ваши тексты — отредактируйте их; без этого каталога сервер не стартует) и записывает ключи в `.env`. Неинтерактивно: `python cli.py init --from-example company --name "Моя компания"` (флаги `--display-name`, `--channel`, `--contact`, `--platforms`, `--slug`, `--force`).
2. `doctor` — проверяет настройки, профиль (печатает, какой выбран, и каталог его шаблонов), рендер шаблонов, бота и канал, права записи. Завершается с ненулевым кодом при FAIL. Флаги: `--sessions` (проверить живость сессий площадок, медленно), `--send-test` (тест-алерт на `ADMIN_TG_ID`), `--offline` (не обращаться к Telegram API — так его запускает скрипт деплоя).
3. `login <площадка>` — открывает браузер, вы входите в аккаунт вручную, cookie-сессия сохраняется в `data/sessions/`. Доступные площадки перечислены в `python cli.py login --help`.
4. `autopilot` — статьи, лид-магнит, посты для Telegram и экспорт; публикация только с флагом `--publish`.

Кампанию создаёт `python cli.py create-campaign --brand "…" --query "…" --seed "…"`; её ID выводится в ответе, список — `python cli.py list-campaigns`.

## Профиль бренда

Профиль — файл `profiles/<имя>.yaml`. Схема проверяется при старте (`core/profile.py`): неизвестный ключ — ошибка. Готовые примеры, от которых удобно отталкиваться:

- [profiles/example-person.yaml](./profiles/example-person.yaml) — личный бренд, тексты от первого лица («я»);
- [profiles/example-company.yaml](./profiles/example-company.yaml) — компания, тексты от лица команды («мы»).

Основные секции: `kind`, `name`, `display_name`, `aliases`, `voice` (тон, тезисы, `forbidden_words`, `forbidden_topics`), `seo` (целевой запрос и тема), `campaign_id`, `telegram`, `offer_tiers`, `lead_magnets`, `platforms`, `radar`, `generation`, `schedule`, `deploy`.

Как выбирается профиль:

1. переменная `SERM_PROFILE` (имя или путь к файлу);
2. иначе единственный профиль в `profiles/`, имя которого не начинается с `example`;
3. иначе — ошибка с подсказкой. Пример-профили сами не подставляются: чтобы запуститься на примере, задайте `SERM_PROFILE=example-person` явно.

### Свои шаблоны с перекрытием

Встроенные нейтральные шаблоны лежат в [templates/](./templates) (статьи, бот, лид-магниты, посты, промпты, админка). Любой из них можно заменить, не трогая код: положите файл с тем же относительным путём в каталог `profiles/<имя>/templates/` (или укажите другой каталог в `templates_dir` профиля). Шаблоны профиля ищутся первыми, встроенные — запасной вариант. Неопределённая переменная в шаблоне роняет рендер, а не печатает пустоту; `doctor` рендерит шаблоны на вашем профиле.

Личный профиль и его шаблоны (`profiles/*/`) исключены из git и из Docker-образа.

### Расписание автопилота

Когда автопилот публикует статьи и посты в канал, задаёт секция `schedule` профиля. Время — местное для `utc_offset_hours` (по умолчанию 3, МСК), в кавычках:

```yaml
schedule:
  utc_offset_hours: 3
  articles:
    - {days: [mon, tue, wed, thu, fri], time: "10:30"}
  telegram:
    - {day: mon, time: "11:00", slot: insight}
```

Слот `HH:MM` срабатывает один раз в окне 60 минут от `HH:MM` (окно после полуночи относится к дню слота); выполненный слот отмечается в `data/autopilot_state.json` датой слота, поэтому перезапуск внутри окна и публикация, закончившаяся после полуночи, не публикуют повторно и не съедают завтрашний слот. Пост, чей слот наступил, пока публиковалась статья, уходит сразу после неё. Статья — не чаще одного слота в день, слоты статей и слоты постов (каждые между собой) — не ближе 60 минут друг к другу, в том числе через полночь; нарушение — ошибка профиля при старте. `slot` — часть ключа в состоянии: на работающей установке его не переименовывают. Без секции (или без списка `articles` / `telegram`) действует встроенное расписание: статьи по вторникам и четвергам в 10:30, посты пн 11:00, вт 13:00, ср 11:30, чт 13:00, пт 15:00. Текущее расписание показывают `python cli.py doctor` и `/api/autopilot/status` (поле `schedule`, часы расписания — `local_time`).

## Режимы генерации

Задаются в секции `generation` профиля; для отдельного запуска перекрываются флагом `--mode template|llm`.

| Режим | Что происходит |
|---|---|
| `template` | Текст собирается из встроенных (или ваших) шаблонов и полей профиля. LLM и сеть не нужны. Без секции `generation` используется он. |
| `llm` | Модель пишет заголовок, лид и тело; оффер, ссылки и контакты добавляет шаблон. Нужен ключ LLM. |

В режиме `llm` результат проверяется кодом: длина по лимитам площадки, `forbidden_words` / `forbidden_topics`, ссылки и `@handle` только из разрешённых (канал, контакт, бот, `deploy.server_url`). Статьи создаются черновиками (`review_required: true`) и публикуются после одобрения в админке. Без ключа или при ошибке провайдера генерация останавливается с явной ошибкой, молчаливого отката на шаблоны нет.

Полезные флаги `generate` и `autopilot`: `--dry-run` (показать промпты и оценку стоимости без вызова API), `--regenerate`, `--refresh-cache`. Ответы, прошедшие проверки, кэшируются в `data/llm_cache/` отдельно для каждой кампании (`--regenerate` кэш не использует), расходы пишутся в `data/llm_usage.jsonl`; сводка — `python cli.py llm-usage`. Предохранитель бюджета — `LLM_MAX_COST_PER_RUN`.

### Подключение LLM-провайдера

Клиент ходит на `POST {base_url}/chat/completions`, поэтому подойдёт любой OpenAI-совместимый провайдер. Укажите в `.env`:

```bash
LLM_API_KEY=sk-...
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-4o-mini
```

Это алиасы для `POLZA_API_KEY`, `POLZA_BASE_URL` и `SERM_LLM_MODEL`; можно использовать любую из форм. Дефолты (`https://api.polza.ai/v1`, `anthropic/claude-sonnet-5.5`) заменяются вашими значениями. Модель можно задать и в профиле: `generation.model`. Чтобы видеть стоимость, заполните `LLM_PRICE_INPUT_PER_MTOK` и `LLM_PRICE_OUTPUT_PER_MTOK`.

## Конфигурация

Переменные окружения перекрывают значения из `.env`. Актуальный полный файл с описаниями генерируется из схемы настроек:

```bash
python cli.py env-example > .env.example
```

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `OPP_BOT_TOKEN` | Токен Telegram-бота воронки (@BotFather) | пусто |
| `OPP_CHANNEL` | Канал, на который нужно подписаться (`@name` или `-100…`); иначе из профиля | пусто |
| `OPP_CONTACT` | Контакт для обращений; иначе из профиля | пусто |
| `SERM_ACTIVE_CAMPAIGN` | Кампания, лид-магнит которой отдаёт бот | пусто |
| `SERM_TG_BOT_TOKEN` | Токен бота для публикации в канал индексации | пусто |
| `SERM_TG_CHANNEL_ID` | Публичный канал быстрой индексации | пусто |
| `SERM_VK_TOKEN`, `SERM_VK_OWNER_ID` | VK: токен и id владельца стены (для группы — `-123456`) | пусто |
| `POLZA_API_KEY` (`LLM_API_KEY`) | Ключ LLM-провайдера | пусто |
| `POLZA_BASE_URL` (`LLM_BASE_URL`) | Базовый URL OpenAI-совместимого API | `https://api.polza.ai/v1` |
| `SERM_LLM_MODEL` (`LLM_MODEL`) | Модель по умолчанию | `anthropic/claude-sonnet-5.5` |
| `LLM_TIMEOUT`, `LLM_MAX_RETRIES` | Таймаут запроса (с) и число ретраев на 429/5xx | `120`, `3` |
| `LLM_PRICE_INPUT_PER_MTOK`, `LLM_PRICE_OUTPUT_PER_MTOK` | Цена за 1M токенов (для учёта стоимости) | пусто |
| `LLM_MAX_COST_PER_RUN` | Бюджет одного прогона генерации в валюте провайдера (у Polza — рубли; прогон из 7 статей, постов и лид-магнита ≈ 50–100 ₽ на Sonnet 5.5). Пустое значение или `none` — без лимита; `0`, отрицательное или неразбираемое значение (`50р`) — бюджет 0, LLM-прогон отказывает с ошибкой. Лимит работает, только если провайдер возвращает стоимость в ответе или заданы `LLM_PRICE_*`; иначе об этом предупреждают лог и `doctor` | `300` |
| `ADMIN_TOKEN` (`ADMIN_PASSWORD`) | Токен админки; пусто — создаётся при первом старте | пусто |
| `ADMIN_TG_ID` (`TELEGRAM_ADMIN_ID`) | Telegram id для системных алертов | пусто |
| `ADMIN_HOST`, `ADMIN_PORT` | Адрес и порт админки | `127.0.0.1`, `8180` |
| `AUTOPILOT_ENABLED` | `true`/`false` перекрывает файл состояния автопилота | пусто |
| `SERM_PROFILE` | Имя профиля или путь к `profiles/<имя>.yaml` | см. «Профиль бренда» |
| `SERM_DATA_DIR` | Каталог данных (БД, сессии, экспорт) | `data/` в корне проекта |
| `SERM_ENV_FILE` | Путь к файлу окружения, который читают настройки, админка и `cli.py` (туда же админка пишет секреты). Задаётся только в окружении процесса, не в самом файле | `.env` в корне проекта |
| `SERM_DEPLOY_HOST`, `SERM_DEPLOY_KEY`, `SERM_DEPLOY_DIR` | Сервер, SSH-ключ и каталог для `push-sessions` | пусто |

## Безопасность админки

- В Docker админка публикуется только на `127.0.0.1`: порт хоста задаётся `ADMIN_BIND` (по умолчанию `127.0.0.1`) и `ADMIN_PORT` (по умолчанию `8180`). Внутри контейнера процесс слушает `0.0.0.0:8180`, а наружу доступ ограничивает именно проброс порта.
- Чтобы открыть админку снаружи (например, для расширения, синхронизирующего cookie), задайте `ADMIN_BIND=0.0.0.0` в `.env` осознанно и закройте порт файрволом или прокси с TLS.
- При запуске без Docker админка по умолчанию слушает только `127.0.0.1` (`ADMIN_HOST`). Чтобы открыть её на всех интерфейсах, задайте `ADMIN_HOST=0.0.0.0` осознанно и закройте порт файрволом или прокси с TLS; `doctor` предупреждает про `0.0.0.0`.
- Вход в админку — по токену `ADMIN_TOKEN`. Если он не задан, создаётся при первом старте и дописывается в `.env`.
- `.env` и `data/sessions/` содержат токены и cookie-сессии с полным доступом к аккаунтам. Не коммитьте их и не выкладывайте.

## Docker

```bash
cp .env.example .env        # заполните значения
cp profiles/example-company.yaml profiles/<имя>.yaml
echo "SERM_PROFILE=<имя>" >> .env
docker compose up -d --build
```

[docker-compose.yml](./docker-compose.yml) монтирует `./data`, `./.env` и `./profiles` (только чтение) внутрь контейнера. Образ профилей не содержит: без `profiles/` процесс остановится с `ProfileError`. Вход в площадки (`login`) требует видимого браузера, поэтому выполняйте его на своей машине и переносите сессии на сервер командой `python cli.py push-sessions <площадка>` (или `--all`) с `--host`, `--key`, `--remote-dir` либо через `SERM_DEPLOY_*`.

## Деплой на сервер

В [examples/deploy/](./examples/deploy) лежат примеры, а не готовая автоматика:

- [rsync-deploy.sh](./examples/deploy/rsync-deploy.sh) — доставляет код по rsync и пересобирает контейнер. `data/`, `.env` и `profiles/` на сервере не затрагиваются; без `--yes` показывает dry run с удалениями и просит подтверждения. Код сначала попадает в каталог `<dir>.staging`, из него собирается образ и запускается `doctor --offline` на данных сервера; рабочий каталог и контейнер заменяются, только если проверка прошла.

  ```bash
  examples/deploy/rsync-deploy.sh --host user@server --key ~/.ssh/id_ed25519 --dir /opt/serm
  ```

- [github-actions.yml](./examples/deploy/github-actions.yml) — workflow для вашего репозитория; требует секреты `DEPLOY_HOST`, `DEPLOY_DIR`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`. Скопируйте его в `.github/workflows/deploy.yml`.

Профиль копируется на сервер один раз вручную вместе с каталогом шаблонов: `rsync -a profiles/ user@server:/opt/serm/profiles/`. Без `profiles/<имя>/templates/` у своего профиля скрипт деплоя откажется выкатывать код.

## Структура проекта

```text
cli.py              # CLI: init, doctor, login, generate, autopilot, publish, ...
scheduler.py        # демон: админка, бот, автопилот (точка входа контейнера)
config/             # настройки (pydantic-settings), единая схема env
core/               # профиль, генерация (шаблоны и LLM), БД, бот, админка, радар, автопилот
publishers/         # реестр площадок и публикаторы
templates/          # встроенные Jinja2-шаблоны и промпты
profiles/           # профили брендов (example-*.yaml — образцы)
examples/deploy/    # примеры деплоя
extension/          # браузерное расширение для синхронизации cookie
scripts/            # вспомогательные скрипты
tests/              # pytest, golden-снапшоты в tests/golden/
```
